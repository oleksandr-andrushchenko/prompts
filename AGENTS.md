# Repository agent instructions

- Keep `shared` limited to genuinely shared domain models, persistence primitives, validation, and helpers used by both Lambdas.
- Before adding or keeping a helper in `shared`, search its callers across `api-lambda` and `web-lambda`. If it is used by only one Lambda, place it in that Lambda's module; web-only helpers belong in `web-lambda/web_utils.py`.
- Lambda-specific orchestration, page composition, and presentation-oriented query helpers must remain in the owning Lambda.
- Scripts should reuse existing application services and persistence helpers instead of reimplementing domain or storage behavior. Before adding direct DynamoDB, S3, or filesystem operations, search for an existing function that performs the operation and call it so the script preserves normal validation, side effects, and invariants. For example, use `create_prompt`/`update_prompt` for prompt writes and `save_public_file` for public files. Use direct persistence operations only for migrations or repairs that cannot be expressed through the existing application API, and keep that exception explicit and narrowly scoped.
- Maintenance and import scripts should process items incrementally: read or fetch one item, print its plan, complete that item's writes through the application services, report the result, and only then advance to the next item. Do not collect or preflight an entire run before applying its writes unless the task explicitly requires atomic batch behavior. Design reruns to skip completed items so rate limits or later failures preserve earlier progress and can be resumed safely.
- Maintenance and import scripts must default to dry-run behavior and perform writes only when the operator explicitly passes `--apply`. Run them directly against production through the `scripts-production` service in `docker-compose.scripts.production.yml`; do not require a local rehearsal before the production dry run.
- Use stdout as the review surface for maintenance and import scripts. On every dry-run iteration, print one structured record: `input` must contain the source item and `output` must contain the complete DTO and arguments that would be passed to the application service, including the full prompt template and source metadata, together with whether it would be created, resumed, unchanged, or skipped. Do not emit separate candidate and outcome records for the same dry-run item. Do not create review, plan, or dry-run manifest files, and do not add tests specifically for one-off import scripts unless the task explicitly requests them.
- Keep persisted import `source` metadata minimal and purpose-driven. Store only stable fields required for provenance, attribution, and rerun matching, such as the importer identity, stable source/container and item IDs, canonical source URL, and original publication time. Do not persist raw source records, reactions or engagement counts, media inventories or hashes, export checksums, duplicate timestamps, derived identifiers, model hints, or other volatile/redundant fields unless application behavior explicitly consumes them. Keep the complete raw item under dry-run `input` and operational media details in the dry-run plan instead.
- Keep source-specific import scripts, exports, overrides, and other source artifacts untracked under existing ignore rules. Do not name or describe import sources in committed documentation or reusable application code; keep committed guidance and comments source-neutral.
- Do not rely on wildcard imports or accidental re-exports for new dependencies; import names explicitly and remove imports that are not referenced.
- Prefer native Bootstrap classes and components for UI changes; avoid modifying `static/styles.css` unless the requirement cannot be implemented cleanly with Bootstrap.
